# M3 交付说明 · 失败中心（Failure Center）

> 目标：把「某某 Case 失败了」升级为「这次回归有 N 个失败，实际只有 M 个问题」。

> 全部验收使用真实 SQLite + 真实 Demo 站 + 真实 Chromium，无 Mock。

## 2. 数据模型

### 2.1 新增表（3 张）

**`failure_fingerprints`** —— 一次失败的确定性指纹，`fingerprint` 唯一。

```
id · fingerprint · strategy · failure_type · exception_type
normalized_message · normalized_expected · normalized_actual
page_url · request_method · request_url · http_status
locator · step_action · sample_message · created_at · updated_at
```

**`failure_groups`** —— 一个分组 = 规则认为属于同一个实际问题的一组失败。

```
id · project_id · fingerprint_id · title · category
rule_id · rule_reason · status(OPEN/RESOLVED/IGNORED)
first_seen_at · last_seen_at
occurrence_count · failed_case_count · failed_run_count · flaky_count
latest_run_id · latest_case_result_id · created_at · updated_at
```

**`failure_occurrences`** —— 一次「某个分组又出现了」，是指向真实证据的锚点。

```
id · failure_group_id · fingerprint_id · run_id
case_result_id · attempt_id · step_result_id
case_status · is_flaky · category · dedupe_key · created_at
```

### 2.2 已有表新增字段

| 表 | 字段 | 说明 |
|---|---|---|
| `step_results` | `console_summary`、`network_summary` | 该步骤窗口内的 console / 网络现场 |
| `step_results` | `request_method`、`request_url`、`http_status` | 最能解释这次失败的 HTTP 异常 |
| `step_results` | `js_error` | 页面未捕获脚本异常 |
| `failure_occurrences` | `category` | 每一次出现自己的分类 |

### 2.3 索引与唯一约束

```
UNIQUE  failure_fingerprints.fingerprint
UNIQUE  failure_groups(project_id, fingerprint_id)      -- 并发安全的最终保障
UNIQUE  failure_occurrences.dedupe_key                  -- 幂等键
INDEX   failure_groups.project_id / fingerprint_id / status / category
INDEX   failure_groups(project_id, last_seen_at)         -- 列表默认排序
INDEX   failure_occurrences.failure_group_id / fingerprint_id / run_id / case_result_id
INDEX   failure_occurrences(failure_group_id, created_at) -- 分组详情历史
INDEX   failure_occurrences.category
```

索引只加在两个真实查询路径上，没有盲目铺。方案 §55 说「以实际查询计划为准」，
这里就是那两条：列表 `WHERE project_id=? ORDER BY last_seen_at DESC`、
详情历史 `WHERE failure_group_id=? ORDER BY created_at DESC`。

## 4. 真实验收（M3-01 ~ M3-14）

全部由 `scripts/selftest_m3.py` 驱动，失败都是真实 Chromium 打在真实 Demo 站上产生的。

### M3-01 Fingerprint：不同 ID 必须同指纹

- **输入**：3 个用例分别打开 `/api/orders/10001`、`/api/orders/10002`、`/api/orders/10003`，接口被注入 500
- **实际结果**：3 个用例全部 FAILED，指纹 `0ea18dd6…` 只有一个
- **数据库结果**：`failure_fingerprints` 仅 1 行，`request_url = http://127.0.0.1:8100/api/orders/{id}`
- **UI 结果**：失败中心该行「影响 3 个用例 / 3 次出现」

### M3-02 同问题聚合：10 个 Case → 1 个 Group

- **输入**：10 个用例各自完整走一遍「登录 → 打开订单页 → 选择商品 → 填数量 → 提交订单 → 断言无错误横幅」，注入 `orders_500`
- **实际结果**：Run `7827ea26b390`，15 个用例全 FAILED（10 下单 + 3 订单接口 + 2 搜索）
- **数据库结果**：`failure_groups` 该 Run 只产生 **3 行**，其中 POST /orders 一行
  `failed_case_count=11`（10 个稳定失败 + 此前的 Flaky 用例，同一指纹）
- **UI 结果**：列表只显示 3 行分组，不是 15 行失败

### M3-03 不同 API 必须分开

- **输入**：同时注入 `orders_500` 与 `search_500`
- **实际结果**：`GET /search?q=键盘` 500 与 `POST /orders` 500 落在两个不同分组
- **数据库结果**：两行 `failure_groups`，`fingerprint_id` 不同
- **UI 结果**：列表中两行，指纹分别指向 `/search` 与 `/orders`

### M3-04 HTTP 500 的完整链路

- **输入**：`orders_500`，断言「下单没有报错」
- **实际结果**：步骤 9 `assert_not_visible` FAILED；分类 **PRODUCT_BUG**，规则 **PRODUCT_HTTP_5XX**，策略 **HTTP_ERROR**
- **数据库结果**：`failure_fingerprints.http_status = 500`、`request_method = POST`；
  `step_results.http_status = 500`
- **UI 结果**：详情抽屉显示规则说明「业务接口返回 500，且无环境层证据（非网关 5xx、无网络异常）」

> 说明：方案允许此处判 UNKNOWN。这里判 PRODUCT_BUG 的依据是
> **步骤窗口内确实捕获到了该接口的 500 响应**（不是靠「文本里有 500」猜），
> 且已排除网关 5xx 与网络异常。证据是结构化采集的，可以在 UI 上逐条核对。

### M3-05 Locator Missing → AUTOMATION_ERROR

- **输入**：`missing_element` 故障（首页问候语不渲染），断言 `home-greeting` 可见
- **实际结果**：`AssertionError: 元素在 15000ms 内未变为可见（定位器 testid=home-greeting）`
- **数据库结果**：分类 `AUTOMATION_ERROR`，规则 `AUTO_ELEMENT_NOT_FOUND`
- **UI 结果**：分类标签「自动化问题」，规则说明标注「需人工确认是否为功能异常」——
  这类证据本质上最弱，理由写在界面上，而不是悄悄给个定论

### M3-06 Network Failure → ENVIRONMENT_ERROR

- **输入**：环境 `base_url` 指向 `http://127.0.0.1:9099`（本机无监听）
- **实际结果**：`net::ERR_CONNECTION_REFUSED`，分类 `ENVIRONMENT_ERROR`，规则 `ENV_CONNECTION_REFUSED`
- **数据库结果**：`step_results.network_summary` 记录失败请求
- **UI 结果**：分类标签「环境问题」

### M3-07 Missing Data → DATA_ERROR

- **输入**：`missing_data` 故障，下单返回「测试数据不存在：下单所需的商品 SKU 已被清理」
- **实际结果**：断言实际值捕获到该文案，分类 `DATA_ERROR`，规则 `DATA_MISSING`
- **数据库结果**：`failure_groups.category = DATA_ERROR`
- **UI 结果**：分类标签「数据问题」

### M3-08 Flaky

- **输入**：`flaky_once` + `retry_count=1`，第一次下单 500、第二次成功
- **实际结果**：尝试序列 `['FAILED', 'PASSED']`，最终 `CaseResult = FLAKY`（不是 PASSED）
- **数据库结果**：`failure_groups.category = FLAKY`、`rule_id = FLAKY_ATTEMPT_SEQUENCE`、
  `flaky_count = 1`；对应 `failure_occurrences.is_flaky = 1`、`category = FLAKY`、
  `attempt_no = 1`（指向第一次失败的那次尝试）
- **UI 结果**：分类标签「Flaky」，详情里出现历史行标 Flaky
- **统计**：`/api/flaky/statistics` 显式返回分母（全部用例执行次数）与计算定义

### M3-09 RetryPolicy 按分类区分（真实执行次数，不是只看策略表）

| 分类 | 策略值 | 开启 `fail_retry` 后实际尝试次数 |
|---|---|---|
| PRODUCT_BUG | 0 | **1** ✅ |
| ENVIRONMENT_ERROR | 1 | **2** ✅ |
| AUTOMATION_ERROR | 0 | **1** ✅ |
| DATA_ERROR | 0 | **1** ✅ |

生效策略（`GET /api/retry-policy`）：
`{"PRODUCT_BUG":0,"ENVIRONMENT_ERROR":1,"AUTOMATION_ERROR":0,"DATA_ERROR":0,"FLAKY":1,"UNKNOWN":1}`

### M3-10 显式 retry_count 兼容

- **输入**：`PRODUCT_BUG` 场景 + 显式 `retry_count=1` + 未开 `fail_retry`
- **实际结果**：真实跑了 **2 次** ✅ —— 显式配置没有被分类默认值 0 压低
- **对照**：同场景开 `fail_retry`、`retry_count=0` 时只跑 1 次（M3-09）

### M3-11 跨 Run 聚合

- **输入**：同一指纹的计划连续再执行 2 次
- **实际结果**：分组数量始终不变；`occurrence_count` 与 `failed_run_count` 每次都递增
- **数据库结果**：分组 `8a6f0f726953` 最终 `occurrence=15 / 影响用例=15 / 影响执行=6`
- **UI 结果**：趋势表列出最近 6 次相关执行

### M3-12 Failure Center 聚合与钻取

- **输入**：一次回归 15 个失败用例
- **实际结果**：聚合为 **3 个 FailureGroup**
- **完整链路实测**（数据库直查，非推测）：


- **UI 结果**：分组 → 出现历史 → 点执行 ID 跳到执行详情，用例自动展开

### M3-13 幂等

- **输入**：对同一个 Run 连续调用 2 次 `POST /api/runs/{id}/analyze-failures`
- **实际结果**：两次都返回 `occurrences: 0`（没有新建）
- **数据库结果**：分组数量 6 → 6，每个分组的
  (occurrence_count, failed_case_count, failed_run_count) 快照完全一致

## 9. 已知问题

### 9.1 产品限制（真实存在，未回避）

1. **Class 与 Retry 的 `fail_retry` 语义是新赋予的。** `RegressionPlan.fail_retry`
   字段 M1 就预留了，但此前没有任何代码使用它。M3 用它作为「系统自动重试」的开关：
   `retry_count>0` 显式优先，`retry_count=0 且 fail_retry=True` 才走分类策略。
   **这么做是为了不动 M1/M2 的既有行为** —— 若 retry_count=0 就自动补重试，
   历史计划的执行行为会整体改变，M2 的验收用例也会全部失效。

2. **规则顺序与方案 §14 有两处有意偏离**（已写在 `classifier.py` 顶部注释里）：
   ENVIRONMENT / 服务端 5xx / JS 异常都排在 AUTOMATION 之前。理由是
   「页面崩了所以元素找不到」若先判自动化错误，会把测试人员引向定位器这个错误方向。
   不影响任何一条 M3 验收项（M3-04/05/06/07 的证据互斥）。

3. **AUTOMATION_ERROR 用在「元素找不到」上是宽松的。** 元素缺失既可能是定位器失效，
   也可能是功能异常（产品 bug）。方案 M3-05 明确要求判 AUTOMATION_ERROR，
   实现照办，但把这条局限写进了 `rule_reason`，界面上能看到。

4. **指纹粒度取决于采集到的信号质量。** `http_status` 取的是步骤窗口内
   「5xx > 网络失败 > 最后一个 4xx」的优先级选择；若同一窗口内有多个不相关的 5xx，
   归因可能指向后发生的那一个。

5. **UNKNOWN 占比偏高**（16 个指纹里 6 个 UNKNOWN）。这是原则性结果，不是实现问题；
   M5 的 AI 分析正是为这批证据不足的失败准备的。

6. **M3 只从 M3 上线后的 Run 开始建立失败数据。** 历史 Run 不自动补算
   （方案 §48 明确不允许偷偷补算）。需要补算时用
   `POST /api/runs/{id}/analyze-failures` 显式触发。

7. **M2 遗留未变**：`/storage` 静态证据目录无访问控制；Playwright 同步 API

## 10. 下一阶段建议：M4（CI Integration）

**M4 只做 CI 接入，不做 AI、不做企微。**

建议顺序：

1. **CLI 先行**（`cli/testflow/`）：`testflow run --plan smoke --env test`，
   退出码 **0=全通过 / 1=有测试失败 / 2=执行系统错误**。
   M3 已经把「失败」和「错误」在数据层严格分开了（FAILED vs ERROR、
   `failure_groups.category` 已经区分产品/环境/自动化/数据），退出码直接映射即可，
   **不需要重新判断** —— 这是 M3 给 M4 省下的最大一块工作。
2. **GitLab CI 触发**：`POST /api/ci/gitlab/trigger` + Token 校验 + 计划识别 +
   防重复触发（用 `(project_id, pipeline_id, plan_id)` 幂等键，M3 的幂等写法可复用）。
3. **Commit 关联**：`execution_runs` 的 `commit_sha / branch / pipeline_id / pipeline_url`
   M1 就在，只需在 CLI 与 Webhook 里填上，并在执行详情与失败分组上展示。
4. **`status` 查询命令**：`testflow status --run-id xxx`，返回 M3 的分组摘要
   （几个问题、各归哪一类），而不是几十条失败。

不建议放进 M4：企微通知（M5）、AI 分析（M5）、Runner 横向扩展
（当前单 Worker 够用，等真有并发压力再说）。

### 对 M5 的接口准备（M4 不做，但值得现在就知道）

M3 已经把 M5 需要的东西全部摆好了：

- `failure_groups.category == "UNKNOWN"` 就是 AI 该介入的**精确入口**，
  不用给 AI 喂全量失败
- `failure_occurrences` → `step_results` 的 8 类证据（截图/Trace/Video/HAR/console/network/DOM/log）
  就是 AI 的输入材料
- `FailureGroup.rule_id / rule_reason` 是规则给出的初步判断，可作为 AI 的对照基线
- 企微通知的聚合粒度**天然就是 FailureGroup**，方案 §12 要求的「一次通知覆盖 24 个用例」
  不需要额外实现
