## 6. 数据流

```
ExecutionRun
  → FailureGroup（M3 聚合结果）
  → FailureOccurrence（代表出现 = 最近一次）
  → StepResult（失败步骤 + 归因信号）
  → Artifact（证据清单）
        │
        ▼
  Analysis Eligibility ── 不通过 ──► 结束（确定性分类已经足够）
        │ 通过（category == UNKNOWN 或规则显式要求）
        ▼
  Evidence Builder（文本裁剪 + 脱敏 + 证据指纹）
        ▼
  AI Provider（OpenAI-compatible；失败不影响 Run）
        ▼
  结构化 FailureAnalysisResult（schema 校验，非法则一次修复重试）
        ▼
  failure_analyses（追加 revision，不覆盖旧的）
        ▼
  测试人员 Review（CONFIRMED / MODIFIED / IGNORED）
        ▼
  Alert Engine（按 FailureGroup 去重聚合）
        ▼
  Notification Provider（企微 Webhook，最多 3 次递增重试，异步）
        ▼
  notification_logs
```

## 7. 状态流

**Analysis**（独立于 FailureGroup.status）

```
PENDING → RUNNING → COMPLETED
                  → FAILED（AI 返回非法 JSON 或调用失败）
                  → CANCELLED
Review：UNREVIEWED → CONFIRMED | MODIFIED | IGNORED
```

**Alert**

```
OPEN → ACKNOWLEDGED → FIXING → REVERIFY → RESOLVED
OPEN → IGNORED
```
禁止跳状态：`ACKNOWLEDGED → RESOLVED` 不允许（必须先经过 FIXING/REVERIFY），
每次转换都有独立 API，非法转换返回 400。

**NotificationLog**

```
PENDING → SENDING → SENT
                 → FAILED（重试耗尽）
```

## 8. 幂等规则

| 对象 | 幂等键 | 行为 |
|---|---|---|
| Analysis | `sha256(failure_group_id + occurrence_id + evidence_fingerprint + prompt_version + provider + model)` | 命中且状态为 COMPLETED → 直接返回已有；FAILED → 允许新 revision；`force=true` → 强制新 revision（`revision_no` 递增，**不覆盖旧行**） |
| Alert | 一个 FailureGroup 同时只能有一个「活动告警」 | 部分唯一索引 `WHERE status IN ('OPEN','ACKNOWLEDGED','FIXING','REVERIFY')`；已存在则**更新** `last_seen / occurrence_count / failed_run_count`，不新建 |
| NotificationLog | `alert_id + channel + content_hash` | 已有 SENT 记录则跳过（内容变了 `content_hash` 变，才会再发） |

**为什么 Alert 用部分唯一索引**：和 M4 的 CI 幂等同理 —— 用全表唯一会把「告警解决后
同一个问题再次出现」这种正常情况挡死。历史上的 CLOSED 告警要多条，
活动告警只能有一条。

## 9. 兼容性风险与对策

| 风险 | 对策 |
|---|---|
| 触碰 `execution/service.py` | 只在末尾追加钩子；try/except 全包；异步执行；不改任何既有语句 |
| AI / 企微未配置 | 一律降级：`ai_enabled` 为假 → 分析接口返回 503 并说明原因；通知直接记 SKIPPED，不报错、不影响 Run |
| AI / 企微调用失败 | 只写 analysis.status=FAILED / log.status=FAILED。**Run、CaseResult、StepResult、FailureGroup.category、Alert 状态都不改** |
| 新增迁移 | 009 只建表与索引，幂等，不改 M1~M4 任何列与数据 |
| Alert 状态被自动化改坏 | 状态机是白名单式；`RESOLVED` **只能由人工 API 触发**，引擎永不自动置 RESOLVED |
| 通知风暴 | Alert 按 FailureGroup 去重 + NotificationLog 按 content_hash 去重，两层 |
| 前端 | 只追加区块，不动既有列表与抽屉结构 |
| M1~M4 回归 | 全部脚本继续跑；不修改、不删除任何既有断言 |

## 10. 明确不做（方案 §26）

不重写执行器 / Fingerprint / Classifier / RetryPolicy / M2 Retry / Stop / M4 CI；
不引入 Kafka / Kubernetes / 微服务 / 多租户；不自动建 Bug、不改代码、不提交 Git；
AI 不决定 PASS/FAIL、不认定责任人、不关闭 Failure Group、不把 UNKNOWN 改成 PRODUCT_BUG；
不做大规模前端重构。
