# M4 交付说明 · CI Integration

> 目标：让外部 CI **可靠、幂等、可追踪**地触发 TestFlowCI，并拿到最终 Run 结果。
> M4 只做 CI 接入，**不做 AI、不做企业微信、不做定时调度**。

一句话概括这一阶段的工程约束：**CI 只是触发入口，不是新的执行器。**
网页、CLI、GitLab 三个入口最后汇到同一条 `create_run` → `dispatch_run` → `execute_run_sync`
→ M3 失败分析链路，执行逻辑一行都没有复制。

## 2. 数据库

### Migration

| 版本 | 名称 | 内容 |
|---|---|---|
| 7 | `007_ci_idempotency` | CI 幂等的**部分唯一索引** |
| 8 | `008_base_url_override` | `execution_runs.base_url_override` |

继续用 `schema_migrations`，未引入 Alembic。SQLite 可运行，模型层 PostgreSQL 兼容。

### 新增字段（1 个）

```
execution_runs.base_url_override  VARCHAR(255)  DEFAULT ''
```

`--base-url` 的落点。**不新开 `ci_provider` / `ci_job_id`** ——
提供方可以从 `trigger_source` 推导，job id 由 `pipeline_id` 覆盖，
按方案 §25「不要设计十几个未来不用的字段」，不加。

### 新增索引 / 唯一约束

```sql
CREATE UNIQUE INDEX uq_execution_runs_ci_idempotency
    ON execution_runs (project_id, plan_id, pipeline_id)
    WHERE pipeline_id <> '' AND trigger_source IN ('CI', 'CLI', 'GITLAB')
```

**为什么必须是「部分」唯一索引**（这一点和方案 §13 的字面写法有出入，是本阶段最重要的设计决定）：

方案给的幂等键是 `(project_id, pipeline_id, plan_id)`。但如果做成全表唯一，会打死两个正常操作：

1. **手动执行**的 `pipeline_id` 是空串 —— 同一个计划第二次手动跑就被自己的幂等约束挡住；
2. **手动重跑失败用例**（M2 的能力）会继承原 Run 的 `pipeline_id` —— 它是一次新执行，
   不是同一个 Pipeline 事件，却被判成重复。

所以加了两层限定：只在 `pipeline_id` 非空、且触发来源是 CI 类时才生效。
语义变成「**同一个 Pipeline 事件 + 同一个计划，只能有一个 Run**」，
这既是方案 §13 真正想要的效果，也不误伤手动操作。

### 迁移安全性

迁移后逐表核对行数，未出现异常减少：
`projects 30 / test_cases 263 / test_suites 23 / execution_runs 172+ / case_results 353+ /
step_results 2330+ / artifacts 8666+ / failure_fingerprints 16 / failure_groups 62 /
failure_occurrences 202`。

### 鉴权设计

CI Token 与网页端 JWT 是**两条独立通道**：

- 网页用户：`Authorization: Bearer <jwt>`
- CI 机器：`X-TestFlow-Token: <TESTFLOW_CI_TOKEN>`

已验证 **CI Token 不能拿来调网页接口**（`/api/projects`、`/api/failures` 仍返回 401）。

几个刻意的选择：

- **Token 没配 = 接口关闭**（503），不是放行。否则「忘了配」会静默变成开放入口。
- 比较用 `hmac.compare_digest`，不用 `==`（字符串比较短路，能被逐字节试探）。
- 401 只回「无效」，**不回显用户传入的值，也不泄漏正确 Token**（有断言覆盖）。
- CLI **不提供 `--token` 参数**：命令行参数会留在 `ps`、shell history、CI job log 里。

## 5. Exit Code

真实验证（都是**子进程退出码**，不是函数返回值）：

| 场景 | 真实 Run 状态 | Exit Code | 验证方式 |
|---|---|---|---|
| 3 用例全通过 | `PASSED` | **0** | M4-02，真实 Chromium 跑通 |
| 业务失败（HTTP 500） | `FAILED`，分组 `PRODUCT_BUG` | **1** | M4-03，注入 `orders_500` |
| 被测环境连不上（`ERR_CONNECTION_REFUSED`） | `FAILED`，分组 `ENVIRONMENT_ERROR` | **1** | M4-04，指向无监听端口 |
| 计划不存在 | 无 Run | **2** | M4-05 |
| PROD 环境（安全门禁） | 无 Run | **2** | M4-05 |
| 缺 `--plan`（argparse） | 无 Run | **2** | M4-05 |
| 缺 / 错 CI Token | 无 Run | **2** | M4-05 |

**核心边界（方案 §4）已经验证成立：**

> 被测环境失败 ≠ TestFlowCI 系统失败。
> M4-04 里目标环境连接被拒，TestFlowCI **成功完成了测试并准确报告了环境问题**，
> 所以是 Exit 1（测试有未通过），不是 Exit 2（平台故障）。

映射只写在 `backend/app/ci/service.py::run_exit_code` 一处，CLI **不重新判断业务结果**，
只负责把服务端算好的 `exit_code` 变成进程退出码。判断权只有一处，
Web 与 CI 不可能给出不同结论。

### 触发端点

```http
POST /api/ci/gitlab/trigger
X-TestFlow-Token: <TESTFLOW_CI_TOKEN>     # 或 X-Gitlab-Token（GitLab 原生 Webhook）
```

支持的两种来源：

**A. GitLab 原生 Pipeline Webhook** —— `project` 是对象，计划/环境靠 pipeline 变量带出来：

```json
{"object_kind": "pipeline",
 "object_attributes": {"id": 182, "ref": "main", "sha": "abc123",
                       "url": "https://gitlab.example/g/-/pipelines/182",
                       "variables": [{"key": "TESTFLOW_PLAN", "value": "smoke"},
                                     {"key": "TESTFLOW_ENV", "value": "test"}]},
 "project": {"path_with_namespace": "group/app", "web_url": "https://gitlab.example/group/app"},
 "user": {"username": "zhangsan"}}
```

**B. CI Job 直接调用** —— 最可控，GitLab 注入的变量原样转发。

> 开发中踩到的坑：一开始用 Pydantic 严格模型收 Webhook 载荷，`project` 声明成 `str`，
> 结果真实载荷里它是对象，直接 422。**Webhook 是 GitLab 发的，它不会按我们的模型改载荷** ——
> 现在接口收裸 dict，只对我们真正需要的字段做判断。

### 不做项目映射表

方案 §11 提到「GitLab Project → TestFlowCI Project 映射」。本版**没有建映射表**：
那需要一张表加一个维护入口，而 CI Job 里本来就知道要跑哪个 TestFlowCI 项目，
多这张表只是给运维加负担。Webhook 形态用 `path_with_namespace` / `name` 去匹配项目名，
匹配不上就明确 400 让调用方在 pipeline 变量里显式给 `TESTFLOW_PROJECT`。

## 7. 幂等

| 测试 | 请求次数 | 最终 Run 数 |
|---|---|---|
| M4-10 顺序重复 | 3 | **1**（`created` 依次为 `true, false, false`） |
| M4-11 并发幂等 | **10 并发** | **1** |
| 单元测试并发 | 10 线程 × 独立 Session | **1**（`created=True` 恰好 1 次） |

并发测试刻意**不用 TestClient**（它不是为多线程设计的），而是像 10 个并发 HTTP 请求那样
每个线程各开一个 Session —— 每个 Session 一条独立连接，这才是真正的并发路径。
数据库里按幂等键核对，确实只有 1 行。

**双保险**：应用层先查一次（省掉大部分重复请求）+ 数据库唯一索引兜住并发，
捕获 `IntegrityError` 后 `rollback` 再重查（失败的事务在 SQLAlchemy 里是「中毒」状态，
不 rollback 后续任何查询都会继续抛）。

反向验证（不能被幂等误伤）：
- 不同 `pipeline_id` → 各自建 Run ✅
- 不带 `pipeline_id` 的重复请求 → 各自建 Run ✅（手动执行不被挡住）

5. 幂等与并发幂等（数据库唯一索引 + 应用层双保险）
6. Exit Code 0 / 1 / 2 真实验证

8. 生产门禁继承（CLI 绕不过）
9. M1/M2/M3 全量回归不下降

### 9.2 未完成

1. **真实 GitLab Pipeline 端到端验收**（无可用 GitLab 实例）
2. Google/GitHub/Actions、Jenkins 等其他 CI —— 方案本就不在 M4 范围
3. **CI Cancel → TestFlowCI Cancel**：方案 §20 明确说第一版不做。
   现在 GitLab 取消 Pipeline 不会停止 TestFlowCI 的 Run，两者独立。

### 9.3 已知限制

1. **`--no-wait` 返回 0**。此时 CLI 无法知道测试结果，退出码只代表「触发成功」。
   实现里会打一条醒目警告，文档与 `--help` 都写明了。CI 里请用默认的 `--wait`。
2. **`--base-url` 覆盖要过安全门禁**。覆盖后的主机必须在该环境的 `allowed_hosts` 里，
   否则被拦。所以它不能用来绕过门禁，只能在同一白名单内换地址。
3. **幂等键不含环境**。同一个 Pipeline + 同一个计划、但换环境触发的第二次请求会命中已有 Run。
   这是刻意的（Pipeline 事件只有一个），若确实需要按环境区分，说明「同一个 Pipeline 跑两次同计划」
   是正常需求，那时应该把 environment 加进幂等键 —— 目前没加。
4. **`pipeline_id` 长度上限 64**，超长会被截断（GitLab 的数值 ID 远小于此）。
5. **JSON schema 与方案 §8 的示例略有出入**：§8 给的是扁平 `failure_groups: {total, PRODUCT_BUG: 2}`，
   §18 给的是嵌套 `{total, categories: {...}}`。两处不一致，**统一采用 §18 的嵌套形式**
   （它是被明确标注为响应 schema 的那一份），保证 ci-status 与 CLI 输出只有一种形状。
6. `/api/ci/meta` 会遍历所有项目，项目非常多时会变慢 —— 它只在报错提示时调用，不在主路径上。

### 9.4 M4 顺手修掉的 1 个既有缺陷

`backend/app/execution/service.py::resolve_case_ids` 的第 4 级兜底（计划既没有套件也没有
case_ids 时）**没有按项目过滤** `CaseFlowBinding`，会捞到其他项目的用例。
M4 改成按 `run.project_id` 过滤。现有 M1/M2/M3 验收用例都走套件或 case_ids 路径，
不经过这条兜底，所以行为不变，只是修掉了一个跨项目泄漏的隐患。

## 12. 下一阶段建议：M5（AI Failure Analysis + 企业微信通知）

**只建议，不开始。**

M3 已经把 M5 需要的东西全部摆好了，这决定了 M5 的天花板很高、工作量却不大：

1. **AI 的精确入口已经存在**：`failure_groups.category == "UNKNOWN"`。
   全库 16 个指纹里 6 个是 UNKNOWN —— 规则明确承认「证据不足」的那批，
   正是 AI 该介入的范围。不需要给 AI 喂全量失败。
2. **证据材料现成**：`failure_occurrences` → `step_results` → 8 类 Artifact
   （截图/Trace/Video/HAR/console/network/DOM/log）已经按 attempt 分好目录。
3. **对照组现成**：`rule_id` / `rule_reason` 是规则给出的初步判断，
   AI 结论可以与它比对，跑偏了能立刻发现。
4. **通知的聚合粒度天然正确**：企业微信通知的单元就是 FailureGroup ——
   方案 §12 要求的「一次通知覆盖 24 个用例」不需要额外实现。
5. **企业微信通道已经预留**：`settings.wecom_webhook_url` 与 `notification_enabled` 字段一直在。

建议顺序：**AI Provider 适配层 → UNKNOWN 失败的证据打包 → 结构化结论
（summary/root_cause/evidence/related_commit/suggested_owner/confidence）→
确认/修改/忽略 → 企微聚合通知（Webhook 起步）**。

M5 需要守住的既有原则（写在 M3 代码里的）：AI 不判 PASS/FAIL、不自动定 Bug、不自动指定责任人；
证据优先于结论；测试人员拥有最终确认权。
