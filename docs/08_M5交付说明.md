`id project_id failure_group_id failure_occurrence_id run_id provider model status analysis_key revision_no prompt_version evidence_fingerprint

## 7. AI Provider

```
AIProvider（抽象）
├── OpenAICompatibleProvider   name=openai_compatible, supports_vision=True
└── FakeAIProvider             name=fake（仅测试，行为可编排）
```

契约：`analyze_failure(context, *, repair_hint="") -> ProviderResponse`。
Provider 不写数据库、不认识 FailureGroup、不做幂等 —— 那些都是 service 的事。
`repair_hint` 放在契约里而不是让 service 拼消息：「怎么把话说给这个模型听」本来就该 Provider 管。

**只依赖 `httpx`**（项目已有），不引入任何厂商 SDK。
配置：`AI_PROVIDER / AI_BASE_URL / AI_API_KEY / AI_MODEL / AI_TIMEOUT / AI_MAX_RETRIES`，
全部从环境变量读，**不写代码、不进 Git**。

实现里处理的真实问题（都实测过）：

| 问题 | 处理 |
|---|---|
| 模型爱包 ` ```json ` | 解析前剥壳，再退一步截取首尾大括号之间的内容 |
| 部分网关不支持 `response_format` | 遇到相关 400 自动摘掉它重试一次 |
| 5xx / 429 / 超时 | Provider 内部按 `AI_MAX_RETRIES` 重试（退避 1s、2s） |
| 400 / 401 / 403 | **不重试**（参数或凭据问题，重试一百次也一样） |
| 错误信息可能回显请求头 | 所有错误文本过 `_redact()`，把 key 掩掉 |

## 8. Evidence Builder

按方案 §5 的证据优先级：`step → http_status → request_url → console → network → dom →
screenshot → trace/har → video → log`。

**先裁剪，再送出去。** 一次失败可能有十几 MB 的 Trace、整页 DOM，全塞进 Prompt 既贵又没用
（模型看不见二进制），还会把关键信息淹没。限额集中在 `EvidenceLimits`：

```
max_total_chars 12000 · step_error 2000 · console 1500 · network 1500 · dom 2000 · log 1500
max_artifacts 12 · max_images 1 · max_image_bytes 2MB
```

**全部先脱敏。** 复用 `utils/redact.py`。Prompt 是整个系统里唯一会把数据带出内网的地方，
所以脱敏在这里是必须项。`test_evidence_redacts_secrets` 直接断言环境变量里的密码
和错误信息里的 token 都不在证据包里。

**默认不读二进制。** Trace / HAR / Video 只登记引用（名字、大小、步骤号）；
截图只在 Provider 声明 `supports_vision` 时才读，且限 1 张、限 2MB。
DOM 会先去掉 `<script>` / `<style>` / 内联 style —— 整页 HTML 里 90% 是噪声。

**`evidence_fingerprint` 刻意排除易变字段**（Run ID、出现次数、时间）。
如果把 `occurrence_count` 算进指纹，缓存永远命中不了，幂等就形同虚设。
`test_evidence_fingerprint_ignores_volatile_fields` 就验这一点。

## 9. Alert Engine

**聚合单位是 FailureGroup，不是失败用例、也不是 Run。**

```
10 个用例同一个根因  →  1 条告警（failed_case_count = 10）
同一个分组连续 3 次 Run →  还是那 1 条，occurrence_count 与 failed_run_count 在涨
```

严重级别用**确定性规则**（`alerts/rules.py`）。级别决定「谁的手机半夜会响」，
这种判断必须可解释、可复现、可争论，而「模型觉得挺严重」既不能复现也没法讲理：

| 分类 | 级别 | 规则 ID |
|---|---|---|
| PRODUCT_BUG 且 影响 ≥10 用例 或 ≥3 次执行 | CRITICAL | `ALERT_PRODUCT_WIDE` |
| PRODUCT_BUG（其余） | ERROR | `ALERT_PRODUCT` |
| ENVIRONMENT_ERROR | ERROR | `ALERT_ENVIRONMENT` |
| UNKNOWN | WARNING | `ALERT_UNKNOWN` |
| AUTOMATION_ERROR / DATA_ERROR | WARNING | `ALERT_TEST_SIDE` |
| FLAKY | INFO | `ALERT_FLAKY` |

级别**只升不降**：一个问题从 CRITICAL 掉回 WARNING 只可能是这轮影响的用例少了，但它还没被修。
级别往下掉会让人以为好转了，那是最危险的假信号。

## 10. WeCom Provider

只做**群机器人 Webhook**（方案 §16 的第一版范围）。自建应用（能真正 @人）需要
corpid / secret / agentid 三件套，起步成本高得多，留到后续。

实现里处理的真实问题：

| 问题 | 处理 |
|---|---|
| 群机器人的 key 在 URL 里 | `safe_url()` 掩码；错误信息、日志、NotificationLog 里都不能出现完整地址 |
| 企业微信对 HTTP 状态码不敏感 | 200 也可能 `errcode != 0`，**必须解析 body 的 errcode** |
| 有些错误值得重试 | `45009`（超限）/ `-1`（系统繁忙）→ 可重试；`93000`（webhook 无效）/ `40001`（secret 无效）→ 不重试 |
| markdown 上限 4096 字节 | 渲染层截断到 1800 字符，Provider 再兜一次 |

## 11. NotificationLog

一次投递记一行，`attempt_count` 在**同一行**上累加（不插新行，否则重试次数数不清）。
去重键是 `(alert_id, channel, content_hash)`：内容变了（例如影响用例数增加）才会再发一条。

**发送失败只写自己这张表。** 不改 Alert 状态、不改 Run、不改任何测试结果 ——
送信失败和问题是否修复之间没有任何因果关系。日志里会把「本次投递尝试几次」与
「这一行累计尝试几次」分开写清楚，避免误读成「一次调用重试了 7 遍」。

## 12. Review 状态机

```
（AI 侧） status:       PENDING → RUNNING → COMPLETED / FAILED / CANCELLED
（人侧）   review_status: UNREVIEWED → CONFIRMED / MODIFIED / IGNORED
```

- 非法 review 值被 Pydantic 拒掉（422）
- 记录 `reviewed_by` / `reviewed_at` / `review_comment`（备注也过脱敏）
- **确认 ≠ 解决**：不改 `FailureGroup.status`、不关分组、不改任何测试结果

## 13. Reverify 流程

```
Alert FIXING
   ↓ POST /api/alerts/{id}/reverify
复用 M2 失败用例重跑：create_run(case_ids=原失败用例, source_run_id=原Run, rerun_mode="verify")
   ↓
alert.reverify_run_id = 新 Run，status = REVERIFY
   ↓ 新 Run 跑完，引擎自动评估
问题仍在 → 退回 OPEN（重新进入处理流程）
问题消失 → 停在 REVERIFY，等人工 RESOLVED
```

**引擎永远不会自动置 RESOLVED。**「这一轮没再出现」不等于「修好了」——
可能是没跑到、可能是环境没起来。只有人能说解决了。
`RESOLVED` 也只能从 `REVERIFY` 来：不允许 `OPEN → RESOLVED`，那等于没验证就宣称修好了。

   方案 §7 明确说不能认定责任人，建映射表反而会诱导人把「建议」当「定责」

### 20.2 设计上的取舍

5. **AI 自动分析在 Run 结束后于后台线程执行**，不是同步。所以 Run 刚结束的那一刻
   去查分析可能还是空的（自测里用 `wait_until` 等它落地）。方案 §19 要求通知异步，
   AI 同理 —— 但代价是「完成时机」不可精确预测。
6. **通知默认静默**：全局开关开了还不够，回归计划自身的「发送企业微信通知」也要打开。
   这是尊重 `notification_plans.notification_enabled` 字段的原意（M1 就预留了），
   代价是新装的系统不会「自己开始发消息」。自测里专门验了这一条。
7. **`analysis_key` 含 occurrence_id**，所以同一个分组在**不同 Run** 里出现时
   会各算一次分析（证据指纹相同但代表出现不同）。
   这是有意的：现场可能不同。但也意味着「同一个错误反复出现」会重复调用 AI ——
   如果实际用起来觉得费 token，可以把 occurrence_id 从 key 里去掉，
   只用 evidence_fingerprint（那是一行改动，但要接受「不同现场复用同一份结论」）。
8. **`notification_logs.attempt_count` 是累计值**（同一行累加），
   不是「本次投递的尝试次数」。判断「这次重试了几次」要算增量。
   UI 列名已改为「累计尝试」以免误读。

### 20.3 开发中踩到并修掉的真问题

| # | 问题 | 根因 | 修法 |
|---|---|---|---|
| 1 | **`TypeError: can't subtract offset-naive and offset-aware datetimes`** | **SQLite 的 `DateTime(timezone=True)` 读回来会丢时区**。写进去是 aware，`db.refresh()` 后变 naive，相减直接抛异常。M2 之所以没踩到，是因为它在同一个 Session 里设完就开始算，中间没 refresh —— 属于侥幸 | 新增 `utils/timeutil.py`：耗时统一用 `time.perf_counter()`（单调时钟，与数据库字段解耦），需要比较数据库时间时用 `ensure_utc()` |
| 2 | **Provider 注册表是空的** | 注册发生在 `providers/__init__.py`，但没有地方 import 它，报错还是最没线索的「可用：无」 | 包 `__init__` 里显式 import + `get_provider()` 里兜底自动注册 |
| 3 | **antd 在两个汉字的按钮文字中间自动插空格**：渲染成「确 认」「修 改」「忽 略」，导致按文字定位的自动化全部失效 | antd 的 `autoInsertSpace` 默认开启 | `ConfigProvider button={{ autoInsertSpace: false }}`（顺带让中文按钮词距正常了） |
| 4 | 通知发送失败的日志写「尝试 7 次」 | 用了**累计** attempt_count，读起来像一次调用重试了 7 遍 | 日志拆成「本周期尝试 N 次，该内容累计 M 次」 |
| 5 | 告警场景验收失败（M5-17） | **我的测试顺序错了**：上一段结束时把故障关掉了，「问题仍在」的前提根本不成立。产品行为其实是对的（重新验证真的通过了 → 停在 REVERIFY） | 调整场景顺序，并把这个坑写进脚本注释 |
