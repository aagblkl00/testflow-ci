### 迁移机制（M2 从零引入）

M1 只有 `Base.metadata.create_all()`，它对「给已有表加列」无能为力。M2 引入
`backend/app/migrations/`：

- `schema_migrations` 表记录已应用版本；
- 每个迁移是幂等函数（自己判断表/列是否已存在），可反复执行；
- SQLite 与 PostgreSQL 通用（列类型按方言取，DDL 为标准 `ADD COLUMN`）。

**为什么不用 Alembic**：本项目迁移需求是线性的（只增表、只加列，不改列类型、不删列），
引入 Alembic 要增加依赖 + 维护 `versions/` 目录，收益不匹配。若后续出现改类型/删列的需求，
再迁到 Alembic。

已应用版本：

```json
{
  "applied": {"1": "001_baseline", "2": "002_execution_center", "3": "003_backfill_null_defaults"},
  "current_version": 3
}
```

`003` 是修补：`002` 给 `rerun_mode` 加列时没带 DDL 默认值，导致 M1 时期的历史行该列为 NULL，
接口序列化报 `Input should be a valid string`。已回填为空串，并在代码里做了防御性兜底。

## 4. 执行器修改

文件：`backend/app/execution/playwright_executor.py`、新增 `backend/app/execution/control.py`

| 改动 | 说明 |
|---|---|
| 停止控制 | 新增 `RunControl`：进程内 Event（inline 即时）+ DB 标志轮询（跨进程）。执行器在**步骤边界**与 **wait 的 200ms 切片**检查停止信号；命中后当前步骤记 `CANCELLED`，后续步骤记 `SKIPPED` |
| 关闭顺序 | 停止或结束时按 `page.close()` → `context.close()` → 取视频 → `browser.close()`。顺序错了会拿到还没 flush 的视频文件 |
| Retry 目录 | `case_dir` 由调用方按 `attempts/{n}/` 指定，执行器无感知，天然保证每次尝试证据隔离 |
| Video | `context(record_video_dir=..., record_video_size=1280x720)`；关闭后把 Playwright 的随机文件名原子重命名为 `recording.webm` |
| HAR | `context(record_har_path=..., record_har_mode="full", record_har_omit_content=True)`；不记响应体，避免文件膨胀与敏感响应落盘 |
| 新增状态 | `STEP_CANCELLED`、`OUTCOME_CANCELLED`、`StoppedByUser` 异常 |
| blocked 标记 | 环境被门禁拦下时返回值带 `blocked=True`，上层据此跳过无意义重试 |
| **不再做任何删除** | 见下方「已知问题」第 1 条 |

### 停止粒度（诚实说明）

- **步骤边界**：立即生效；
- **`wait` 动作**：200ms 切片轮询，实测停止延迟 **0.6 ~ 1.0s**；
- **单个 locator 操作 / 页面导航进行中**：**无法安全中断**。Playwright 同步对象不能跨线程调用，
  强行 `close()` 会破坏协议状态。这类操作会在返回后立刻生效，理论上限为该步骤配置的 `timeout`。

这不是偷懒，是同步 API 的固有限制。要完全消除这个窗口需要改用 Playwright 异步 API
（task 可取消），代价是重写执行器，M2 不做。

## 14. 当前已知问题

### 必须知道的 3 个（M2 期间踩到并已修复，记录原因避免重犯）

1. **执行器里做文件删除会打断整次执行**
   最初用 `video.save_as()` 另存后 `unlink()` 清理 Playwright 的原始视频文件，
   结果触发了运行环境的删除安全策略，抛 `SystemExit` 直接把执行进程打断。
   → 改为 `os.replace()` 原子重命名（移动，不是删除），**代码内现在没有任何删除动作**。
   教训：执行器里不要做破坏性文件操作。

2. **`StepResult.attempt` 整型列被同名关系覆盖**
   我新增 `attempt = relationship(...)` 想关联 attempt 记录，而 `attempt` 这个列名在 M1 已存在
   （步骤自身的重试序号）。同名把列定义覆盖掉，实例化时报
   `'int' object has no attribute '_sa_instance_state'`。
   → 关系改名为 `attempt_record`。

3. **重跑时会继承上一个 Run 的停止标志**
   新 Run 若 `cancel_requested` 为真会立刻自杀。→ 启动时显式重置。

### 遗留（按里程碑归属）

| # | 问题 | 归属 |
|---|---|---|

## 15. 下一阶段 M3 建议

M3 的主题是**失败中心**，这是整个产品价值最集中的一块。基于 M2 已具备的能力，建议：

### 已经有基础，可直接用
- 失败证据齐全（截图 / Trace / 视频 / HAR / console / network / DOM / 步骤日志）
- `StepResult.expected / actual / error` 字段完整，断言失败的实际值已保留
- FAILED 与 ERROR 语义已严格区分（业务失败 vs 环境/策略失败）——这是规则分类的前提
- Demo 站 6 个故障开关已就位（`login_500` / `search_500` / `orders_500` / `orders_slow_ms` / `missing_element` / `flaky_once`）
- FLAKY 判定已完成，M3 的 Flaky 统计可以直接站在 `case_result_attempts` 上做

### 建议的 M3 范围
1. **Failure Fingerprint**（确定性算法，不用 AI）
   归一化动态段：`/order/12345` → `/order/{id}`；异常类型 + 归一化错误 + assertion + endpoint + 状态码 → hash
2. **FailureGroup 聚合**
   一次执行 20 个失败但只有 3 个根因时，失败中心显示 3 个组而不是 20 条
3. **规则分类 6 类**：PRODUCT_BUG / ENVIRONMENT_ERROR / AUTOMATION_ERROR / DATA_ERROR / FLAKY / UNKNOWN
   优先规则，UNKNOWN 才留给 AI（M5）
4. **Flaky 统计**：最近 N 次执行里的失败比例、失败后重试成功次数、连续失败
5. **按失败类型分级的重试策略**（把上面第 4 条遗留一起做掉）
6. **故障注入验收**：方案 §49 的 5 种情况，特别是「10 个用例同一个接口 500 → 只形成 1 个 FailureGroup」

### 建议的实现顺序
先做 Fingerprint + 聚合（数据层，可用脚本验证）→ 再做规则分类 → 最后做失败中心页面。
理由：聚合是失败中心的地基，页面依赖它；先做页面会导致返工。

### 不建议放进 M3
AI 失败分析（M5）、企业微信（M5）、CI（M4）、元素自愈。按里程碑排期走。
