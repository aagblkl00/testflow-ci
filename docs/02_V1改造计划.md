## 零、已确认的 4 项基线决策

| # | 决策 | 结论 | 影响 |
|---|---|---|---|
| 1 | 数据/队列底座 | **渐进式双底座** | SQLAlchemy 一套模型，本地 SQLite 先跑通；提供 `docker-compose.yml`（PG+Redis），装 Docker 后改 `.env` 一行即切。执行层 `EXECUTOR_MODE=celery｜inline` 自动降级 |
| 2 | 代码基线 | **新建独立仓库 + 移植器官** | 新建 `<项目根目录>`，移植执行器 / ActionSpec / AI Provider / 报告骨架，其余重写。Lodestar 保持原样不受影响 |
| 3 | 真实目标站点 | **自建 Demo 站 + 内部被测站点 双目标** | 自建站内置故障注入开关（承载方案第 49 条 5 种故障），内部被测站点做真实环境冒烟 |
| 4 | 企业微信接入 | **双通道，先 Webhook** | `WeComWebhookProvider` 先跑通，预留 `WeComAppProvider`（可 @人） |

## 五、已知风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **本机无 Docker** | 验收项「Docker Compose 完整启动」无法当场验证 | 配置写好并自测 `docker compose config` 语法；装上 Docker 后一条命令验证。**其余 37 项不依赖 Docker** |
| C/D 盘空间紧张 | 依赖安装可能失败 | 后端依赖装进独立 venv（不复用 workbuddy 全局）；前端 node_modules 落 D 盘 |
| Windows 下 Celery | `prefork` pool 在 Windows 不可用 | 默认 `--pool=solo`；同时保证 inline 模式功能等价 |
| 26 张表一次建齐 | 后期改表成本高 | Alembic 管理，只增不删；先建齐再写业务 |
| 前端工作量最大 | 拖慢整体 | 按方案第 54 条，UI 优先级最低。M1 只做**能用的骨架**，不做美化，M7 才收口 |
| 自建 Demo 站也是开发量 | 占用时间 | 极简单文件 FastAPI + 原生 HTML，只做 6 个页面 + 故障注入开关，不引入前端框架 |
| AI 厂商/配额 | 分析功能不可用 | Provider 可插拔；配置缺失时自动跳过 AI，只走规则分类（不影响主流程） |
| 企微 webhook 无法 @人 | 通知到位率 | 双通道预留；webhook 阶段用「建议关注模块」+ 详情链接替代 @人 |

## 六、开发纪律（我给你的汇报格式）

**每完成一个里程碑，我按这 7 项汇报，不含糊：**

1. 完成了什么
2. 修改/新增了哪些文件（带路径）
3. 怎么启动
4. 怎么验证（可复制粘贴的命令）
5. 验证结果（真实输出，不是"应该没问题"）
6. 当前剩余问题
7. 下一阶段是什么

**不做**：只写代码不跑、只写接口不跑、只写假数据、只做 Mock、只做页面。
