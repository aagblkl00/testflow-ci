## 2. TestFlow 最小领域模型（12 张表）

只建闭环必需的 12 张（方案 §4 的 11 张 + users 用于登录）：

| 表 | 作用 | 关键字段 |
|---|---|---|
| `users` | 登录与角色 | username / password_hash / role(ADMIN·TESTER·VIEWER) / wecom_userid |
| `projects` | 项目 | name / description / repository_url |
| `environments` | 执行环境 | base_url / variables / environment_type / allowed_hosts / read_only / browser |
| `test_cases` | 测试用例 | case_code / name / module / priority / tags / preconditions / expected |
| `test_steps` | 用例的人工步骤 | sort_order / action / locator / value / expected / timeout |
| `automation_flows` | 可执行流程 | name / version / engine / variables / **definition(JSON: steps[])** |
| `case_flow_bindings` | **用例 ↔ 流程 绑定** | case_id / flow_id / enabled |
| `regression_plans` | 回归计划 | environment_id / **case_ids(JSON)** / trigger_type / browser / retry_count |
| `execution_runs` | 一次执行 | status / trigger_source / commit_sha / pipeline_id / 各项计数 / duration_ms |
| `case_results` | 用例级结果 | run_id / case_id / flow_id / status / duration_ms / error_message |
| `step_results` | 步骤级结果 | step_no / action / status / **expected / actual** / duration_ms / error / 截图路径 / page_url / DOM 路径 |
| `artifacts` | 证据索引 | run_id / case_result_id / step_result_id / type / path / size |

### 三个关键设计决策

**① 用例与流程不用硬关联字段**

方案 §16 明令禁止 `test_cases.automation_flow_id` 这种写法。TestFlow 中二者只能通过
`case_flow_bindings` 建立关系，一个用例可以绑定多个流程（当前取第一个启用项），
执行时按绑定关系解析：

```
TestCase → CaseFlowBinding → AutomationFlow → PlaywrightExecutor → CaseResult
```

**② 用 JSON 列承载「暂时不需要独立生命周期」的多值字段**

`regression_plans.case_ids`、`environments.variables`、`automation_flows.definition` 都是 JSON。
理由：M1 不需要按用例维度查询计划，做成关联表属于过早设计。
SQLite 与 PostgreSQL 对 SQLAlchemy `JSON` 类型都支持，切换底座不用改代码。
真正需要独立生命周期时（如 M2 的 TestSuite）再升级为关联表。

**③ 状态词表对齐方案 §17，但用字符串而非数据库 Enum**

`ExecutionRun`: QUEUED / RUNNING / PASSED / FAILED / PARTIAL / CANCELLED / ERROR
`CaseResult`: PENDING / RUNNING / PASSED / FAILED / SKIPPED / FLAKY / ERROR
`StepResult`: PASSED / FAILED / SKIPPED / ERROR

用字符串是为了 SQLite 与 PostgreSQL 行为一致（PG 原生 Enum 在跨库迁移时很麻烦）。

### 尚未建的表（按里程碑排期）

| 表 | 归属 | 为什么现在不建 |
|---|---|---|

## 5. 迁移风险

| 风险 | 实际表现 | 处置 |
|---|---|---|
| **Playwright 版本与浏览器缓存不匹配** | 实测踩到：新装 1.63 需要 `chromium-1243`，本机只有 `1187`，直接报 `Executable doesn't exist` | 已锁定 `playwright==1.55.0` 对齐缓存。README 写明：换版本就要重下浏览器 |
| **Starlette 新版 `TemplateResponse` 签名变更** | 实测踩到：`TemplateResponse(name, context)` 报 `unhashable type: dict`，Demo 站 500 | 已改为 `TemplateResponse(request, name, context)`。**这次失败反而成了闭环的第一次真实战果**：Failure 有截图、有 Trace、有 DOM 快照，定位只用了一次 |
| **Lodestar 执行器与业务强耦合** | 原执行器直接 import `mission_engine`（使命/支付/缺陷草稿） | 只摘出 4 个安全函数重建 `security.py`，其余不带 |
| **Lodestar 数据层是裸 sqlite3，无 ORM** | `store.py` 1443 行没法直接搬 | 只借表设计，实现全部重写为 SQLAlchemy，换 PG 时零改动 |
| **循环依赖风险** | `service.py` ↔ `workers/__init__.py` 互相 import | 已把 import 全部放到函数内部，实测导入无环 |
| **Windows 下 Celery 不能用 prefork** | 未实测（M1 不装 Redis） | README 已写明必须 `--pool=solo`；容器内可用默认 |
| **无 Docker，compose 未实际验证** | `docker compose` 命令本机不存在 | `docker-compose.yml` 与 `docker/Dockerfile` 已写好并逐项核对；装上 Docker 后需跑一次 `docker compose config` 与 `up -d` 才算真验证。**其余 37 项验收不依赖 Docker** |
| **`/storage` 静态目录无鉴权** | 当前任何知道路径的人都能下载证据 | M1 有意的取舍（本地开发）。方案 §33 的脱敏已在数据层生效，但访问控制必须放 M6，已记入 M6 任务 |
| **执行器在进程内线程跑** | inline 模式下浏览器与 API 同进程，崩溃会互相影响 | inline 只用于开发与单机；正式模式切 Celery worker 即隔离 |
| **前端体积 1.2 MB（gzip 388 KB）** | Vite 提示 chunk 过大 | M1 不做优化，M6/M7 再按需拆包 |

### 自测发现并修复的 3 个真实缺陷

这 3 个问题**只有跑起来才会暴露**，是本次自测最有价值的部分：

| # | 缺陷 | 影响 | 修复 |
|---|---|---|---|
| 1 | **断言失败时 `actual` 丢失** | 方案 §9 要求每步展示 Expected / Actual，但断言抛异常时实际值随异常一起丢了 —— 而失败时 actual 恰恰最该被看到 | 新增 `AssertionFailure(AssertionError)` 携带 `actual`；所有断言改用它；`_run_step` 的异常分支提取 `getattr(exc, "actual", "")`。错误前缀仍是 `AssertionError`，用户看到的信息不变 |
| 2 | **空日志产生 0 字节文件** | 没有 console 输出/网络错误时仍写 `console.log`、`network.log`，导致证据目录出现 8 个 0 字节文件，污染证据列表 | 只在有内容时才落盘 |
| 3 | **自测断言本身过严**（非产品缺陷） | 原来无条件要求存在 console/network 证据，但「没有输出」本来就不该有文件 | 改成真正有意义的断言：无 HTTP 错误时不产生空证据 + **有 500 的执行必须留下 network 记录** |

另外补了一条容易被忽略的检查：**缩略图必须真实解码**（`naturalWidth > 0`）。
因为坏图的页面整页截图和正常页面长得一模一样，只有查解码状态才发现得了。实测 10/10 解码成功。
